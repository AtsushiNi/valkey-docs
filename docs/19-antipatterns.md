# 19. アンチパターン・障害パターン集

> この章は、各章の「注意」を一覧にしたものです。詳しい説明は、各行の「詳しく」の章を参照してください。

## 要点

- Valkey の障害や不具合の多くは、**RDB の感覚のまま使うこと**（01 章「RDB の感覚が通用しない点」）と、**1本のスレッドでコマンドを実行する仕組み**（01 章「アーキテクチャ」）から来ています。
- 設計・実装・運用の各段階で起きやすいパターンを、症状・原因・防ぎ方の形で一覧にしました。**設計レビュー、コードレビュー、障害の振り返り**のときに、この表で漏れがないかを確かめてください。
- 特に起きやすく、影響の大きいものを、最初の「重要な 10 件」にまとめています。

## 表の見方

| 列 | 内容 |
|---|---|
| パターン | 何をしてしまうか |

| 防ぎ方・気づき方 | 何をすれば防げるか、どうすれば気づけるか |
| 詳しく | 説明している章 |

## 重要な 10 件

| # | パターン | 症状 | 防ぎ方 | 詳しく |
|---|---|---|---|---|
| 1 | 本番で `KEYS` や、ビッグキーへの `HGETALL` を実行する | 数秒間、すべてのリクエストが止まる | `SCAN` を使う。要素の数を先に確かめる。権限で禁止する | [02 章](02-basics-and-keys.md)・[03 章](03-string-and-hash.md)・[15 章](15-security.md) |
| 2 | 本番のプライマリを手動で再起動する | レプリカがあっても、すべてのデータが消える | 再起動しない。フェイルオーバーは `TestFailover` で試す | [18 章](18-upgrade-and-maintenance.md) |
| 3 | 本番のキーに上書きしながら全件を入れ替える | 新旧のデータが混ざって見える。削除された商品が残る | 新しい世代を作ってからポインタを切り替える | [09 章](09-loading-swapping-deleting.md) |
| 4 | キャッシュ向けのエビクションの設定（`allkeys-*`）を使う | データが黙って消え、API が「存在しない」と応答する | `noeviction` か、有効期限のないデータだけの `volatile-lru` にする。`Evictions` を監視する | [11 章](11-memory.md) |
| 5 | 入れ替えの方式の2世代分のメモリを見込まない | 作り直しの途中でメモリが足りなくなる | ロード中の最大の使用率で見積もり、しきい値を逆算する | [11 章](11-memory.md)・[16 章](16-monitoring.md) |
| 6 | ローカル（単一ノード）だけで試し、本番（クラスター）で初めて動かす | `CROSSSLOT` エラー、パイプラインの動きの違いが本番で出る | CI でクラスターモードの結合テストを動かす | [10 章](10-local-and-testing.md) |
| 7 | redis-py のタイムアウトとリトライを既定値のままにする | Valkey の障害で、1つのリクエストが1分前後待たされ、API 全体が止まる | API の応答時間の上限から逆算して設定する | [08 章](08-fastapi.md) |
| 8 | 作り直しのバッチの成否を監視しない | バッチが止まっても、API が古いデータを返し続けて気づかない | 最後に作り直しに成功してからの時間を監視する | [16 章](16-monitoring.md) |
| 9 | 本体と二次インデックスを別々に更新する | 一覧に、削除した商品や移した商品が出る | 新しい世代ごと作り直す。参照先が見つからない件数を記録する | [04 章](04-set-zset-list-stream.md)・[05 章](05-data-modeling.md) |
| 10 | ホットキー（入れ替えのポインタなど）を見落とす | 1つのシャードだけが限界に達し、全体が遅くなる | アプリのメモリに短時間持つ。ノードごとに監視する | [05 章](05-data-modeling.md)・[09 章](09-loading-swapping-deleting.md) |

## 設計

### データモデリング

| パターン | 症状 | 原因 | 防ぎ方・気づき方 | 詳しく |
|---|---|---|---|---|
| RDB と同じように、後から読み方を足せると考える | 新しい読み取りパターンのたびに、索引の追加・バッチの改修・作り直しが必要になる | 設計にない読み方はできない | 画面と API の仕様から読み取りパターンを洗い出し、合意しておく | [05 章](05-data-modeling.md) |
| `:` で階層を作れると考え、プレフィックスで分割する | 意味のない設計になる | `:` は慣習で、技術的な意味はない（01-9） | 気にするのは1つのキーの大きさと、全体のメモリ量 | [02 章](02-basics-and-keys.md) |
| プレフィックスや DB 番号で、用途を分離できると考える | ある用途の負荷やメモリ不足が、別の用途を巻き込む | 分離の仕組みはない（01-9） | 影響させたくない用途は、クラスターを分ける | [02 章](02-basics-and-keys.md) |
| 1つのキーに要素を増やし続ける（ビッグキー） | 読み書き・削除が全体を止める。シャードが偏る。シャードの増減が遅くなる | 要素の数に比例する操作が、1本のスレッドを占有する | 要素が増え続ける設計を避け、キーを分ける | [03 章](03-string-and-hash.md)・[13 章](13-replication-and-cluster.md) |
| 1つの JSON 文書に、増え続けるデータを入れる | ビッグキーと同じ | 一部だけを読み書きできても、文書の大きさは変わらない | 増え続けるデータは別のキーにする | [07 章](07-json-and-search.md) |
| Hash に長い値（説明文など）を入れる | メモリの使用量が想定より大きく増える | 64 バイトを超える値が1つでもあると、Hash 全体のエンコーディングが変わる | 長い値は別のキーに分ける。実際のデータでメモリを測る | [03 章](03-string-and-hash.md) |
| 埋め込んだ値（カテゴリ名など）を、差分の更新で直し漏らす | 一部の商品に古い値が表示され続ける | 埋め込んだ値は、元のデータを変えても自動では変わらない（01-2） | キー設計書にコピー元を書く。定期的に全件を作り直す | [05 章](05-data-modeling.md) |
| ハッシュタグを付けすぎる | 特定のシャードにデータとアクセスが集中する | 同じハッシュタグのキーは、すべて1つのシャードに置かれる | ハッシュタグは小さな集まりにだけ付ける | [05 章](05-data-modeling.md) |
| 同じスコアの要素の並び順を、数値の順だと考える | ページをまたいだときの並びが期待と違う | 同じスコアの要素は、文字列の辞書順に並ぶ | ID をゼロ埋めする。スコアに並び順の情報を含める | [04 章](04-set-zset-list-stream.md) |
| 値のシリアライズの形式を、後から変える | 新しいアプリが古い形式のデータを読めない | スキーマがなく、古い形式のデータも残っている（01-1・01-8） | 値やキー名にバージョンを持たせる。読む側は古い形式も読めるようにする | [03 章](03-string-and-hash.md) |
| 命名規則を決めずにキーを作る | 同じデータが二重に入る、削除の対象から漏れる | どんな名前でもエラーにならない | キー名を組み立てる処理を1か所にまとめる | [02 章](02-basics-and-keys.md) |
| Stream の件数の上限を決めない | メモリを使い続ける | Stream は自動では縮まない | `MAXLEN` / `XTRIM` で上限を決める | [04 章](04-set-zset-list-stream.md) |

### 構成・容量

| パターン | 症状 | 原因 | 防ぎ方・気づき方 | 詳しく |
|---|---|---|---|---|
| 「作り直せるから、消えても問題ない」と考える | データが空になり、作り直しが終わるまで API が正しく応答できない | 全件の作り直しには時間がかかる | 作り直しの時間を測り、レプリカ・バックアップ・永続化の設定を決める | [01 章](01-what-is-valkey.md)・[12 章](12-persistence-and-backup.md) |
| 「インメモリだから何でも速い」と考える | 大きなデータを一度に取得して、API 全体が遅くなる | 要素の数に比例するコマンドは、メモリ上でも遅く、ほかを止める | 計算量を確かめ、大きなデータは分けて取得する | [01 章](01-what-is-valkey.md)・[02 章](02-basics-and-keys.md) |
| 見積もりを、値の大きさの計算だけで行う | 実際のメモリの使用量が何倍にもなる | 管理用の領域とエンコーディングの違いが含まれていない | 実際のデータを入れて測る | [05 章](05-data-modeling.md) |
| 検索のインデックスのメモリを見積もりに入れない | メモリが足りなくなる | インデックスはデータとは別にメモリを使う | 実際のデータでインデックスを作って測る | [07 章](07-json-and-search.md) |
| 平均のリクエストの量でサイジングする | アクセスの多い時間帯や全件ロード中に、性能が足りない | 負荷は平均の何倍にもなる | 最も負荷の高い時間帯で見積もる | [14 章](14-elasticache-design.md) |
| ECPU を、リクエストの回数だけで見積もる | Serverless の費用が見積もりの何倍にもなる | ECPU は転送するデータの大きさにも比例する。パイプラインでも減らない | 応答の大きさを見積もりに入れる。必要なフィールドだけを読む | [14 章](14-elasticache-design.md) |
| AZ をまたぐ通信の費用を見落とす | 通信量の多い使い方で、費用が膨らむ | ノードベースでは、AZ をまたぐ通信に課金される | 通信量を見積もり、費用に含める | [14 章](14-elasticache-design.md) |
| Serverless の制約を確かめずに選ぶ | 障害のときに、`SLOWLOG` などの調査用のコマンドが使えない | Serverless では、多くの調査用のコマンドが使えない | メトリクスとアプリのログで調べる前提で、監視を設計する | [14 章](14-elasticache-design.md)・[17 章](17-troubleshooting.md) |
| 日本語の文章を valkey-search の TEXT で検索する | 文章の途中の単語で検索しても見つからない | 日本語は単語の間に空白がない | 実際のデータで確かめる。検索エンジンに任せることも検討する | [07 章](07-json-and-search.md) |

## 実装

### アプリ（FastAPI・redis-py）

| パターン | 症状 | 原因 | 防ぎ方・気づき方 | 詳しく |
|---|---|---|---|---|
| リクエストごとにクライアントを作る | 接続の数が急増し、応答が遅くなる | クライアントごとに新しい接続（TLS を含む）が作られる | lifespan で1つ作って使い回す。`NewConnections` を監視する | [08 章](08-fastapi.md)・[15 章](15-security.md) |
| ワーカーのプロセスを分ける前にクライアントを作る | 応答の取り違えや接続エラー | redis-py のクライアントは、プロセスの複製に対して安全ではない | lifespan の中で作る | [08 章](08-fastapi.md) |
| `async def` の中で同期版のクライアントを使う | 待っている間、そのワーカーのほかのリクエストが止まる | 同期の呼び出しがイベントループを止める | `redis.asyncio` を使う | [08 章](08-fastapi.md) |
| パイプラインの `transaction` を明示しない | ローカルと本番で、不可分かどうかが逆になる | 既定値が `Redis` と `RedisCluster` で違う | 必ず明示する | [06 章](06-multi-command.md) |
| パイプラインで送れば、まとめて反映されると考える | 読む側から途中の状態が見える | パイプラインは不可分ではない（01-3） | 不可分にしたいなら、トランザクションか Lua を使う | [06 章](06-multi-command.md) |
| トランザクションが失敗したら、全部取り消されると考える | 一部のコマンドだけが実行された状態が残る | ロールバックはない | `EXEC` の結果を確かめ、再実行できるようにする | [06 章](06-multi-command.md) |
| `HGETALL` などを、要素の数を気にせずに使う | データが増えるにつれて、応答が遅れる | O(N) のコマンドで、N が運用中に増える | 必要なフィールドだけを読む（`HMGET`）。大きいものは `HSCAN` で分けて読む | [03 章](03-string-and-hash.md) |
| 長い Lua スクリプトを書く | 実行中、すべてのリクエストが待たされる | スクリプトは不可分に実行される | 扱う要素の数に上限を設ける | [06 章](06-multi-command.md) |
| `GET` してから `SET` する | 同時に実行すると、更新が失われる | 2つのコマンドの間に、ほかのコマンドが割り込める | `INCR` などの1つのコマンドで済ませる | [02 章](02-basics-and-keys.md) |
| 書き込みを気軽にリトライする | `INCR` などが二重に実行される | タイムアウトしたコマンドも、実行済みのことがある | 何度実行しても同じ結果になる書き込みを使う | [08 章](08-fastapi.md) |
| 参照先が必ずあると考えて読む | エラーになる、または件数が合わない | 参照の整合性はない（01-2） | 参照先がない ID を飛ばし、件数を記録する | [05 章](05-data-modeling.md) |
| 検索・JSON を redis-py の既定の通信方式（RESP3）で使う | 検索の結果が空になる、値がおかしい | valkey-search の応答が、RESP3 の形式に対応していない | `protocol=2` を指定する。実環境で確かめる | [07 章](07-json-and-search.md) |
| `FT.SEARCH` で `LIMIT` を付け忘れる | 10 件しか返らない | 既定は 10 件 | `LIMIT` を必ず付ける | [07 章](07-json-and-search.md) |
| ヘルスチェックに Valkey への `PING` を含める | フェイルオーバーで、すべてのポッドが再起動され、API が止まる | Valkey の一時的な問題で、アプリまで止まる | liveness はアプリ自身だけを見る | [08 章](08-fastapi.md) |
| Valkey が止まったら、すべて RDB から読む | RDB に負荷が集中し、RDB まで止まる | Valkey は、RDB では間に合わない速さのために置いている | RDB に流す量を制限する仕組みとセットにする | [08 章](08-fastapi.md) |
| IP アドレスで接続する | ノードの置き換えの後、接続できない | 置き換えで IP アドレスが変わることがある | エンドポイント（DNS 名）で接続する | [18 章](18-upgrade-and-maintenance.md) |
| フェイルオーバーの後も、古い接続を使い続ける | `READONLY` のエラーが出続ける | 降格した元のプライマリにつながったまま | `READONLY` を接続し直すべきエラーとして扱う | [13 章](13-replication-and-cluster.md) |
| IAM 認証で、トークンを使い回す | 12 時間ごとに接続エラーがまとまって起きる | 接続は 12 時間で切断され、トークンの期限は 15 分 | 接続のたびに新しいトークンを作る | [15 章](15-security.md) |
| 書いた直後に、レプリカから読む | 書く前の値が返る | レプリケーションは非同期（01-4） | 書いた値をすぐに読む処理は、プライマリから読む | [13 章](13-replication-and-cluster.md) |

### バッチ（データの投入・入れ替え・削除）

| パターン | 症状 | 原因 | 防ぎ方・気づき方 | 詳しく |
|---|---|---|---|---|
| Hash を `HSET` だけで更新する | RDB で NULL になった列の古い値が残る | `HSET` は指定しないフィールドに触れない（01-10） | 全体を置き換えるときは、不可分に置き換える | [03 章](03-string-and-hash.md) |
| 1件ずつ書き込む | 全件ロードに何十倍も時間がかかる | 時間のほとんどが通信の往復の待ち | パイプラインで数百〜数千件ずつ送る | [06 章](06-multi-command.md)・[09 章](09-loading-swapping-deleting.md) |
| ロードの前に、空きメモリを確かめない | 作り直しの途中でメモリが足りなくなり、書き込みが失敗する（設定によってはデータが消される） | 入れ替えの間は2世代分のメモリが必要 | ロードの前に空きメモリを確かめ、足りなければ中止する | [09 章](09-loading-swapping-deleting.md)・[11 章](11-memory.md) |
| 全件ロードの量に上限を設けない | ロードの間、本番の API が遅くなる | バッチと API が、1本のスレッドとネットワークを取り合う | スループットに上限を設ける。アクセスの少ない時間帯に行う | [09 章](09-loading-swapping-deleting.md) |
| ポインタを切り替えた直後に、古い世代を消す | 切り替えの直前に読み始めたリクエストが 404 になる | リクエストやアプリのメモリ、レプリカが、まだ古い世代を見ている | 十分な猶予を置いてから消す | [09 章](09-loading-swapping-deleting.md)・[13 章](13-replication-and-cluster.md) |
| 差分の同期だけで運用する | Valkey と RDB が少しずつずれていく | ずれの原因が多く、突き合わせる仕組みもない | 定期的な全件の作り直しと組み合わせる | [09 章](09-loading-swapping-deleting.md) |
| ロックの有効期限を、バッチの時間より短くする | 同じバッチが二重に動く | 期限が切れると、ほかのバッチがロックを取れる | 期限をバッチの最大の時間より十分に長くする | [09 章](09-loading-swapping-deleting.md) |
| 大量のキーを `DEL` で一度に消す | 全体が止まる | `DEL` はその場でメモリを解放する | `UNLINK` を使い、少しずつ消す | [09 章](09-loading-swapping-deleting.md) |
| 同じ TTL で大量のキーを作る | 削除と再読み込みが一時に集中する | 期限が切れる時刻がそろう | TTL にばらつきを加える | [02 章](02-basics-and-keys.md) |
| 期限付きのキーを `SET` で上書きする | 期限がなくなり、いつまでも残る | `SET` は既存の TTL を消す | `KEEPTTL` を付けるか、期限を付け直す | [02 章](02-basics-and-keys.md) |
| 金額を `INCRBYFLOAT` で扱う | 誤差が出る | 浮動小数点数で計算される | 最小単位の整数にして `INCRBY` で扱う | [03 章](03-string-and-hash.md) |

### テスト

| パターン | 症状 | 原因 | 防ぎ方・気づき方 | 詳しく |
|---|---|---|---|---|
| モックで通ったので、Valkey でも動くと考える | 本番で動きが違う | モックは Valkey と同じ動きをする保証がない | Valkey の動きに依存する処理は、実際のコンテナで確かめる | [10 章](10-local-and-testing.md) |
| テストのデータの初期化を、接続先を確かめずに行う | 検証環境や本番のデータが全部消える | どこにつながっていても `FLUSHDB` が実行される | 接続先がテスト用かを確かめる。本番では権限で禁止する | [10 章](10-local-and-testing.md) |

## 運用

### 監視

| パターン | 症状 | 原因 | 防ぎ方・気づき方 | 詳しく |
|---|---|---|---|---|
| `CPUUtilization` で CPU の余裕を判断する | 余裕があるように見えるのに、応答が遅い | コマンドの実行は1本のスレッドで行われる | `EngineCPUUtilization` を見る | [16 章](16-monitoring.md) |
| メモリのしきい値を、一般的な 80% にする | 次の入れ替えでメモリが足りなくなる | 入れ替え中は2世代分が必要 | 入れ替えの方式から逆算する（例: 45%） | [16 章](16-monitoring.md) |
| クラスター全体の平均だけを見る | 特定のシャードの限界に気づかない | 平均では、偏りが隠れる | ノードごとにアラームを設定する | [16 章](16-monitoring.md) |
| 有効期限の付いたキーがあるのに、メモリの上限に近づく | ロックなどの少数のキーだけが消され、バッチが二重に動く | `volatile-*` では、有効期限の付いたキーが優先して消される | 上限に近づく前にアラームで気づく | [11 章](11-memory.md) |
| 接続の数を見積もらない | スケールアウトで接続の上限に近づく | 接続の数はポッドとワーカーの数の掛け算で増える | 最大のポッドの数で見積もり、監視する | [08 章](08-fastapi.md) |

### 保守・調査

| パターン | 症状 | 原因 | 防ぎ方・気づき方 | 詳しく |
|---|---|---|---|---|
| 全員が、すべてのコマンドを使えるユーザーで接続する | 誤った `FLUSHALL` で全データが消える | 権限で防いでいない | 用途ごとにユーザーを分け、危険なコマンドを禁止する | [15 章](15-security.md) |
| 調査のつもりで、重いコマンドを実行する | 本番がさらに遅くなる、止まる | 調査用のコマンドにも重いものがある | 使ってよいコマンドを手順書に書く。重い調査はレプリカで行う | [17 章](17-troubleshooting.md) |
| 接続先の環境を確かめずに操作する | 本番と検証環境を取り違える | — | 接続したら、まずどの環境かを確かめる | [17 章](17-troubleshooting.md) |
| 障害の最中に、原因が分からないまま設定を変える・再起動する | データが失われる。原因の手がかりが消える | 再起動でデータが消えることがある | 影響を確かめてから変える | [17 章](17-troubleshooting.md)・[18 章](18-upgrade-and-maintenance.md) |
| 削除したのにメモリが減らないので、さらに消す | メモリが思うように減らない | 原因が断片化のことがある | 断片化の割合を確かめてから対処する | [09 章](09-loading-swapping-deleting.md)・[11 章](11-memory.md) |
| 検索のインデックスを作り直した直後に、それを使う API を公開する | 検索結果の件数が少ない | バックフィルが終わるまでは、読み込み済みのキーしか対象にならない | `FT.INFO` の `state` が `ready` になってから公開する | [07 章](07-json-and-search.md) |
| アクセス文字列で `-@dangerous` にして、動作を確かめない | 調査やバッチで必要なコマンド（`INFO` など）が使えない | `@dangerous` には運用で使うコマンドも含まれる | 必要なコマンドを個別に許可し、検証環境で確かめる | [15 章](15-security.md) |
| 検証環境で試さずに、本番のバージョンアップを行う | アプリの一部がエラーになり、元に戻せない | バージョンアップは元に戻せない | 検証環境で先に行い、結合テストを通す | [18 章](18-upgrade-and-maintenance.md) |
| サービスの更新を放置する | 期限の後に、自分たちで選んでいないタイミングで適用される | 期限を過ぎると、自動で適用されることがある | 通知を受けたら、適用の予定を決める | [18 章](18-upgrade-and-maintenance.md) |
| バックアップからの復元を試していない | 障害のときに、復元の時間や接続先の切り替えで手間取る | 復元は新しいクラスターになり、接続先が変わる | 検証環境で定期的に試し、手順書を作る | [12 章](12-persistence-and-backup.md) |
| 全件ロード、バックアップ、メンテナンスの時間帯を重ねる | メモリ不足や性能の低下 | どれもメモリと CPU を使う | 時間帯をずらす | [11 章](11-memory.md)・[18 章](18-upgrade-and-maintenance.md) |

## まとめ

- 障害や不具合の多くは、RDB の感覚のまま使うことと、1本のスレッドでコマンドを実行する仕組みから来ています。
- 設計レビュー、コードレビュー、障害の振り返りのときに、この一覧で漏れがないかを確かめます。
- 新しいパターンを見つけたら、該当する章の「注意」と、この一覧の両方に追加します。
