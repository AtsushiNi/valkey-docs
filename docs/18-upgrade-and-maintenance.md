# 18. バージョンアップとメンテナンス

> 前提: [12. 永続化・バックアップ・復旧](12-persistence-and-backup.md)、[13. レプリケーションとクラスター](13-replication-and-cluster.md)

## 要点

- ElastiCache の構成に変化が起きる作業は、**エンジンのバージョンアップ**、**サービスの更新**、**ノードの置き換え**、**スケーリング**の4つです。それぞれ、誰が始めるか、いつ行われるか、アプリにどう影響するかが違います。
- ノードベースでは、多くの変更が**週1回のメンテナンスウィンドウ**で行われます。アクセスの少ない時間帯に設定し、全件ロードやバックアップと重ねないようにします。
- エンジンのバージョンアップは、自動では行われません。**元のバージョンに戻すことはできない**ので、検証環境で確かめてから行います。
- **利用者がプライマリを再起動すると、レプリカがあってもデータが消えます。** 本番のプライマリを手動で再起動してはいけません。
- Serverless では、マイナーバージョンの更新やサービスの更新は、AWS が自動で、停止なしで行います。

## 構成に変化が起きる作業

| 作業 | 誰が始めるか | いつ行われるか | ノードベースでの影響 | Serverless |
|---|---|---|---|---|
| エンジンのバージョンアップ | 利用者 | すぐに、またはメンテナンスウィンドウ | 検証環境で測る（下の節） | マイナー・パッチは自動。メジャーは利用者が始める（どちらも停止なしとされている） |
| サービスの更新（セキュリティの修正など） | 重大なセキュリティの更新は AWS が自動で。それ以外は利用者 | メンテナンスウィンドウ、または利用者が適用したとき | ノードごとに適用される | 自動で、透過的に適用される |
| ノードの置き換え（ホストの OS の更新など） | AWS が予定する（利用者が先に行うこともできる） | 予定された日時（メンテナンスウィンドウ） | 自動フェイルオーバーが有効なら、書き込みを受け付けたまま完了する | — |
| スケーリング | 利用者 | すぐに、またはメンテナンスウィンドウ | オンラインで行えるが、一時的に性能が落ちる（下の節） | 自動 |

## メンテナンスウィンドウ（maintenance window）

| 項目 | 内容 |
|---|---|
| 頻度 | 週1回 |
| 既定 | リージョンごとに決まった 8 時間の範囲から、ランダムな曜日の 60 分が選ばれる |
| 変更 | 自分で設定できる（最大 24 時間） |
| その間に行われること | 保留中の変更（「すぐに適用」にしなかったノードタイプの変更やバージョンアップ）、AWS の予定したノードの置き換え、自動で適用されるサービスの更新 |

| 決め方 | 理由 |
|---|---|
| アクセスの少ない時間帯にする | 一時的な性能の低下や接続の切断の影響を小さくする |
| 全件ロード（09 章）、バックアップ（12 章）と重ねない | どれもメモリと CPU を使うため、重なると影響が大きくなる |
| 既定のランダムな時間帯のままにしない | 業務の時間帯に当たることがある。CDK で明示的に設定する（14 章の `preferred_maintenance_window`） |
| 時刻は UTC で指定する | 日本時間との変換を間違えやすい |

## エンジンのバージョンアップ

### ノードベース

| 項目 | 内容 |
|---|---|
| 始め方 | クラスター（レプリケーショングループ）の設定でエンジンのバージョンを変える。自動では行われない |
| 適用のタイミング | 「すぐに適用」を選ぶと、すぐに行われる。選ばなければ、次のメンテナンスウィンドウで行われる |
| 元に戻す | **できない。** 古いバージョンに戻すには、クラスターを作り直す必要がある |
| パラメータグループ | メジャーバージョンが変わると、パラメータグループのファミリーも変わる。Valkey 9 のパラメータグループは 8 系と互換性がないので、9 用のパラメータグループを用意する（14 章） |
| スケーリングとの関係 | バージョンアップの予定があると、スケールアップが止められることがある |

バージョンアップの最中に、アプリにどれだけの影響（接続の切断、フェイルオーバー、遅延）が出るかは、構成によって違います。**本番と同じ構成の検証環境で、実際にバージョンアップを行い、影響を測ってから**本番で行います。

### 手順の例

| 手順 | 内容 |
|---|---|
| 1 | リリースノートで、変更点を確かめる（挙動が変わるコマンド、使えなくなる設定など） |
| 2 | redis-py が新しいバージョンに対応しているか、新しい機能を使うなら必要なバージョンを確かめる（08 章） |
| 3 | 検証環境でバージョンアップを行い、アプリの結合テストと、バージョンアップ中のエラーの量を確かめる |
| 4 | 本番のバックアップを取る（12 章） |
| 5 | アクセスの少ない時間帯に、本番でバージョンアップを行い、メトリクスとアプリのエラーを監視する（16 章） |

> **注意: 検証環境で試さずに、本番のバージョンアップを行う**
>
> - **何が起きるか**: バージョンアップの後で、アプリの一部の処理がエラーになる。元に戻せないため、急いでアプリを直すか、クラスターを作り直すことになる。
> - **なぜ起きるか**: 新しいバージョンで、コマンドの挙動やエラーの出方が変わることがある。バージョンアップは元に戻せない。
> - **どう防ぐか**: 検証環境で先に行い、結合テストを通す。変更点はリリースノートで確かめる。

### Serverless

| 項目 | 内容 |
|---|---|
| マイナー・パッチバージョン | AWS が自動で最新のものを適用する。AWS のドキュメントでは、アプリへの影響や停止はないとされている |
| メジャーバージョン | 新しいバージョンが出ると、コンソールと EventBridge のイベントで通知される。利用者がキャッシュの設定を変えて行う。停止なしで行われるとされている |

停止なしとされていても、接続が切り直される可能性に備えて、アプリはリトライで回復できるようにしておきます（08 章）。

## サービスの更新

セキュリティの修正などのサービスの更新は、重要度によって、適用の期限の目安が決まっています。

| 重要度 | 適用の目安 |
|---|---|
| critical | 14 日以内 |
| important | 30 日以内 |
| medium | 60 日以内 |
| low | 90 日以内 |

| 項目 | 内容 |
|---|---|
| 重大なセキュリティの更新 | メンテナンスウィンドウで自動で適用される |
| それ以外 | 利用者が適用する（コンソール、CLI）。「期限の後の自動の更新」が有効な更新は、期限を過ぎると、メンテナンスウィンドウで自動で適用される |
| 通知 | `ElastiCache:ServiceUpdateAvailableForNode` のイベント（16 章） |

> **注意: サービスの更新を放置する**
>
> 更新を放置していると、期限を過ぎた後に、自動で適用されることがあります。自分たちで選んだタイミングではなく、メンテナンスウィンドウで行われます。通知を受け取ったら、適用の予定を決め、検証環境で先に適用して影響を確かめます。

## ノードの置き換え

AWS は、ホストの OS の更新などのために、ノードを新しいものに置き換えることがあります。予定は通知されます（`ElastiCache:NodeReplacementScheduled`、16 章）。

| 構成 | 影響 |
|---|---|
| 自動フェイルオーバーが有効（レプリカあり） | 書き込みを受け付けたまま、置き換えが完了する |
| レプリカのないノード | 新しいノードにデータを移す間、そのノードは使えない。データはできるだけ引き継がれるが、保証はない（12 章） |
| 共通 | 新しいノードは、**IP アドレスが変わることがある** |

> **注意: IP アドレスで接続している**
>
> ノードの置き換えで IP アドレスが変わると、IP アドレスを直接指定して接続しているアプリやセキュリティの設定が動かなくなります。接続先は、必ずエンドポイント（endpoint。DNS 名）で指定します。

## スケーリング

| 種類 | 方法 | 影響 |
|---|---|---|
| ノードタイプの変更（スケールアップ・ダウン） | 新しいノードタイプのノードを作り、データを同期してから切り替える | オンラインで行えるが、切り替えのときに読み書きが数秒止まることがある（クラスターモード無効）。小さいノードに変えるときは、データが収まる必要がある |
| シャードの追加・削除（クラスターモード有効） | オンラインでハッシュスロットを移す（13 章） | 移している間、性能が落ちる。256 MB を超える要素を持つキーは移せず、偏りが残ることがある。シャードを減らすときは、残りのシャードにデータが収まる必要がある |
| レプリカの追加・削除 | レプリカのノードを足す・減らす | シャードごとに最大 5 つ。マルチ AZ が有効なままでは、最後のレプリカは削除できない |

スケーリングは、アクセスの少ない時間帯に行い、全件ロードと重ねないようにします。

## プライマリを再起動してはいけない

| 操作 | 結果 |
|---|---|
| 利用者がプライマリを再起動する | **自動のフェイルオーバーは起きない。プライマリは空の状態で戻り、レプリカもデータを消す** |
| フェイルオーバーを試したい | 再起動ではなく、フェイルオーバーを試すための機能（`TestFailover`）を使う。24 時間で 15 シャードまで |

> **注意: 不調を直すつもりで、プライマリを再起動する**
>
> - **何が起きるか**: 遅さや接続のエラーを直すつもりで本番のプライマリを再起動したところ、すべてのデータが消え、API がすべての商品について「存在しない」と応答する。
> - **なぜ起きるか**: 利用者による再起動では、フェイルオーバーは起きず、プライマリは空で戻る。レプリカも、空になったプライマリに合わせてデータを消す。
> - **どう防ぐか**: 本番のプライマリを手動で再起動しない。再起動の権限を IAM で絞る。不調の調査は 17 章の手順で行う。万一データが消えたときに、作り直しのバッチで戻せるようにしておく（12 章）。

## アプリの備え

メンテナンスやスケーリングでは、短い接続の切断や、トポロジーの変化が起きます。アプリは次のように備えます。

| 備え | 内容 |
|---|---|
| リトライとタイムアウト | 短い切断から回復できるようにする（08 章） |
| トポロジーの変化への追従 | クラスター対応のクライアントが、構成を取り直せるようにする（13 章） |
| エンドポイントで接続する | IP アドレスを使わない |
| 影響を測っておく | 検証環境で、フェイルオーバー（`TestFailover`）、バージョンアップ、スケーリングを実際に行い、エラーの量と回復までの時間を測る |

## まとめ

- 構成に変化が起きる作業は、エンジンのバージョンアップ、サービスの更新、ノードの置き換え、スケーリングの4つです。誰が始めるか、いつ行われるかを把握しておきます。
- メンテナンスウィンドウは、アクセスの少ない時間帯に明示的に設定し、全件ロードやバックアップと重ねません。
- エンジンのバージョンアップは元に戻せないので、検証環境で先に行います。メジャーバージョンが変わるときは、パラメータグループも用意し直します。
- サービスの更新は、重要度ごとの期限の目安までに、自分たちで選んだタイミングで適用します。
- ノードの置き換えでは IP アドレスが変わることがあるので、エンドポイントで接続します。
- 本番のプライマリを手動で再起動してはいけません。レプリカがあってもデータが消えます。フェイルオーバーを試すときは `TestFailover` を使います。
- Serverless では、マイナーバージョンやサービスの更新は自動で、停止なしで行われます。それでも、リトライで回復できるようにしておきます。
