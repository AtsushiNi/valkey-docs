## 0. 読者と使われ方（構成の前提）

全員が業務中の限られた時間で、自分で読む。説明会は前提にしない。

| 読者 | 読む時間の目安 | 主に読む部分 |
|---|---|---|
| 事業会社のエンジニア（ベンダーを管理する立場） | 30 分程度 | 概要編の ★ の節 |
| ベンダーの上位者 | 1 時間程度 | 概要編の全体 |
| 実装者・レビュー担当者 | 読み込む（時間の制約なし） | 詳細編の全章 |

→ **詳細編と概要編の2つで構成する。**

- **詳細編（00〜19章、付録）を正本とする。**
  - 各章の冒頭に「要点」を置く
  - 本文は表と箇条書きを中心にし、長い説明は後ろに回す
  - 読者: 実装者・レビュー担当者
- **概要編（`docs/overview.md`）は、詳細編を短くまとめたダイジェストにする。**
  - 目的: 時間のない人が全体像をつかむこと（リスクの判断材料ではない）
  - 図を多めにする。たとえば「Valkey とは」「データがどんな層の構造で置かれているか」を図で示す
  - 節の並びは詳細編の章の順番に合わせる
  - 30 分で読む人向けの節には ★ を付ける
  - 細かい内容は書き写さず、詳細編の該当箇所にリンクする（内容のずれを防ぐ）
  - 詳細編をすべて書き終えてから、最後に書く

## 2. 目次

### 第1部 基礎

#### 00. はじめに（○）
- このドキュメントの目的・対象読者・前提知識
- 対象バージョン（Valkey 9.1 / ElastiCache）
- 例の題材の紹介（§3）
- 読み方のガイド（通読の順番、辞書として引くときの入口）
- 表記ルール（用語、囲み）

#### 01. Valkey とは（○）
- インメモリのキーバリューストアとは。RDB との違い
- 向く用途・向かない用途。正本を RDB に置き、Valkey を読み取り用に使う構成が成り立つ理由
- Redis との関係（数行）
- アーキテクチャ: コマンドを1本のスレッドで実行するモデルと I/O スレッド
  - → 「1つの遅いコマンドが全体を止める」理由。後の章の多くの注意点の根拠になる
- 落とし穴: 「メモリ上にあるからデータは消えてもいい」「何でも速い」という誤解

#### 02. 基本操作とキー（○）
- valkey-cli の基本
- キーと値。キーの命名規則（区切り文字、プレフィックス、長さ）
- 有効期限（TTL）とキーが消える仕組み（アクセス時の削除と定期的な削除）※薄め。コマンドの列挙はしない
- 計算量（O(1) / O(N)）の読み方と、その重要性
- KEYS と SCAN の違い
- 1つのコマンドは不可分に実行されること（アトミック性）
- 落とし穴: 本番で KEYS を使う / TTL の付け忘れ・付けすぎ / 期限切れのキーが一斉に消えて負荷が集中する

#### 03. データ型 (1) String と Hash（◎）
- String: 値の保存、カウンター、SET のオプション（NX / XX / EX / IFEQ）
- Hash: フィールドの操作、HGETDEL（9.1）、フィールド単位の有効期限（9.0。存在を紹介する程度）
- オブジェクトの持ち方の比較
  - JSON にして String に入れる / Hash に入れる / フィールドごとに別のキーにする
- 内部のエンコーディング（listpack とハッシュテーブル）とメモリ使用量
  - → 「小さい Hash はメモリを節約できる」の根拠
- 落とし穴: 巨大な Hash（ビッグキー）/ HGETALL の多用 / シリアライズ形式を後から変える

#### 04. データ型 (2) Set・Sorted Set・List・Stream（○）
- Sorted Set: スコアでの並べ替え、範囲での取得、ページング → 一覧 API の基本形
- Set: タグや所属関係、集合演算
- List（薄め）: 最新 N 件の保持
- Stream（薄め）: どんなものか。差分の同期で使うときの位置づけ（詳しくは 08 章）
- 二次インデックスを自分で作るという考え方（RDB のインデックスとの違い）
- 落とし穴: ZRANGE で全件を取ってしまう / 集合演算の計算量 / インデックスと本体データのずれ

#### 05. データモデリングとキー設計（◎）
- アクセスパターンから設計する（RDB の正規化から考える発想との違い）
- RDB のテーブルを Valkey に写す手順（例の題材を使って）
- 二次インデックス、非正規化、参照の持ち方
- キー数とサイズの見積もり方
- クラスターを見越したキー設計（ハッシュタグ。詳しくは 13 章）
- 落とし穴: 後から読み取りパターンが増えたときの手戻り / ホットキー / キーの命名がぶれる

#### 06. 複数コマンドの扱い（○）
- パイプライン（厚め）: 往復回数（RTT）を減らす。バッチサイズの決め方
- トランザクション（MULTI / EXEC / WATCH）: 何が保証され、何が保証されないか（ロールバックはない）
- Lua スクリプト（EVAL）: サーバー側で不可分に実行する
- Functions（薄め）: ElastiCache Serverless では使えない
- クラスターでの制約（CROSSSLOT エラー）
- 落とし穴: パイプラインとトランザクションの混同 / 長い Lua スクリプトが全体を止める

#### 07. JSON と検索（○）
- valkey-json: 使う場面、Hash との比較
- valkey-search: 属性検索・全文検索・集計。インデックスの作成と更新
- 自前の二次インデックス（04 章・05 章）との使い分け
- ElastiCache での制約（9.0 以降、トランザクションの中で使えない操作）
- 落とし穴: redis-py の JSON・検索 API との相性（RESP3 での応答の解析）/ インデックスが使うメモリ

### 第2部 アプリ開発

#### 08. FastAPI からの利用（◎）
- redis-py の非同期 API（`redis.asyncio`）
- 接続の管理: lifespan で生成・破棄する、依存性注入、コネクションプール
- 単一ノード用クライアントとクラスター用クライアント（`RedisCluster`）。TLS での接続
- タイムアウト、リトライ、バックオフの設定
- RESP3 と `decode_responses`、シリアライズの方針
- Valkey 独自のコマンドの呼び出し方（`execute_command`）
- Valkey に障害が起きたときのアプリの振る舞い（エラーを返す / RDB に切り替える）
- 落とし穴: リクエストごとに接続を作る / タイムアウトを設定しない / フェイルオーバー中のエラー処理 / Redis 専用のコマンドを補完候補から選んでしまう

#### 09. データの投入・入れ替え・削除（◎）
- RDB からの全件ロード（パイプラインを使う、バッチサイズ、スループットの目安）
- 入れ替えの方式
  - バージョン付きのキーとポインタの切り替え
  - RENAME の注意点
  - DB の切り替え（ElastiCache での制約）
- 差分の同期の方式: アプリからの二重書き込み / CDC / Stream。それぞれの整合性
- 冪等性と、途中で失敗したときの再実行
- **データの削除**
  - DEL と UNLINK の違い（DEL が全体を止めうる理由）
  - パターンに一致するキーをまとめて消す方法（SCAN と UNLINK を組み合わせる）
  - FLUSHDB / FLUSHALL の非同期実行（ASYNC）と、Serverless での挙動
  - 期限による自動削除を、古いデータの片付けに使う方法
  - 削除してもメモリがすぐに減らない理由（断片化。詳しくは 11 章）
- **大量データを扱うときの注意**
  - ロード: メモリの余裕を持つ、スループットを調整する、本番のトラフィックへの影響
  - 削除: 少しずつ消す、非同期で消す
  - 読み取り: 大きな結果を分けて取る（SCAN 系のコマンド、範囲を指定した取得）
  - データ量がスナップショット・レプリカの同期・復元にかかる時間に与える影響（詳しくは 11〜13 章）
  - 通信量の上限（ネットワークの帯域）
- 落とし穴: ロード中にメモリが不足する / 入れ替えた瞬間に中途半端なデータが見える / 大量の DEL で全体が止まる / 削除したのにメモリが減らない

#### 10. ローカル環境とテスト（○）
- Docker Compose での構成の概要と、本番（ElastiCache）との差（クラスターモード、TLS）
- テストの方針: 実際のコンテナを使う / fakeredis などのモックを使う。その使い分け
- pytest と非同期テスト、データの初期化
- 落とし穴: ローカルは単一ノードなので、本番のクラスターで初めて CROSSSLOT エラーが出る

### 第3部 インフラ・運用

#### 11. メモリ管理とエビクション（◎）
- maxmemory とエビクションのポリシー
  - キャッシュとして使う場合と、正本から作り直せるデータストアとして使う場合の違い（noeviction など）
- メモリ使用量の内訳と見積もり（データ、オーバーヘッド、断片化、レプリケーション用のバッファ）
- スナップショット時のフォークとコピーオンライト（ElastiCache の予約メモリ）
- ビッグキーの検出と対処
- 落とし穴: メモリが満杯になって書き込みが失敗する / 想定外のエビクションでデータが黙って消える / 断片化

#### 12. 永続化・バックアップ・復旧（◎）
- RDB スナップショットと AOF の仕組み（ElastiCache では AOF を使えない）
- ElastiCache のバックアップ（自動・手動）と復元
- 耐久性のオプション（9.0 以降のトランザクションログ）
- 「バッチで作り直せる」構成で永続化をどこまで使うか: 復旧時間とコストのトレードオフ
- 落とし穴: 再起動・置き換えでデータが空になる / バックアップ中の負荷

#### 13. レプリケーションとクラスター（○）
- レプリケーション: 非同期であること、レプリカからの読み取りと整合性
- フェイルオーバー: 何が起き、アプリからどう見えるか
- クラスター: ハッシュスロット、ハッシュタグ、MOVED / ASK のリダイレクト
- 複数キーの操作の制約、シャードの偏り、ホットキー
- リシャーディング（アトミックなスロット移行）
- 落とし穴: レプリカから古いデータを読む / ハッシュタグの付けすぎでシャードが偏る / フェイルオーバー中に書き込みが失われる

#### 14. ElastiCache の構成選定（◎）
- Serverless かノードベースか（判断基準の表）
- クラスターモードを有効にするか、無効にするか
- ノードタイプとサイジングの手順（メモリ、CPU、ネットワーク）
- マルチ AZ、レプリカの数
- コスト（料金体系と参考の単価）
- CDK（L1）での構成例: CfnServerlessCache / CfnReplicationGroup / CfnParameterGroup / CfnSubnetGroup
- 落とし穴: Serverless の使えないコマンド / ECPU の見積もりの甘さ / AZ をまたぐ通信料

#### 15. セキュリティ（○）
- ネットワークの分離（VPC・セキュリティグループ。ElastiCache に固有の点だけ）
- TLS（転送時の暗号化）と保存時の暗号化
- 認証: AUTH トークン / ユーザーとユーザーグループ（RBAC）/ IAM 認証
- ACL によるコマンドとキーの制限、DB 単位の ACL（9.1）
- CDK での設定例（CfnUser / CfnUserGroup）
- 落とし穴: 本番での default ユーザーの扱い / 認証情報の更新（ローテーション）

#### 16. 監視（◎）
- 見るべき CloudWatch メトリクス（CPU、メモリ、接続数、エビクション、レプリケーションの遅延、ECPU など）
- Serverless とノードベースでのメトリクスの違い
- アラームの設計（しきい値の考え方）と CDK での定義
- アプリ側で取るべきメトリクス（レイテンシ、エラー率）
- 落とし穴: CPUUtilization ではなく EngineCPUUtilization を見るべき理由 / 平均値だけを見る

#### 17. トラブルシューティング（◎）
- 症状ごとの調査手順
  - レイテンシの悪化 / メモリの逼迫 / 接続数の枯渇 / CPU の高騰 / フェイルオーバー
- 調査に使うコマンド（INFO、SLOWLOG、COMMANDLOG、MEMORY USAGE など）と、構成ごとに使えるかどうか
- Serverless でコマンドが使えないときの代わりの手段
- 落とし穴: 調査のつもりで本番に重いコマンドを打つ

#### 18. バージョンアップとメンテナンス（○）
- エンジンのバージョンアップの手順と影響（ダウンタイム、フェイルオーバー）
- メンテナンスウィンドウとサービスの更新
- スケーリング（スケールアップ・スケールアウト）の影響
- 落とし穴: メンテナンス中の接続断に備えていない / バージョンを上げると挙動が変わるコマンド

## 3. 例の題材

**架空の EC サイトの「商品カタログ API」**

正本は RDB（products、categories、inventories などのテーブル）にあり、バッチで Valkey に入れる。
API はユーザーからの読み取りが中心という想定。チームの想定用途と同じ形にした。

| 読み取りパターン | Valkey での持ち方（各章で使う例） |
|---|---|
| ID で商品詳細を取得する | Hash（03 章） |
| カテゴリ別の商品一覧を価格順・人気順で並べ、ページングする | Sorted Set（04 章） |
| タグで絞り込む | Set（04 章） |
| 複数の条件で検索する | valkey-search（07 章） |
| 在庫数 | String・カウンター（03 章） |
| 全件の入れ替え・差分の反映 | 09 章 |

## 6. 用語集（表記ルール）

### 基本方針

- 一般的な技術用語はカタカナで書く（要件 §8）
- 次のものは英語のまま書く
  - 固有名詞・製品名: Valkey、ElastiCache、redis-py、FastAPI など
  - データ型の名前: String、Hash、Set、Sorted Set、List、Stream（コマンドや公式の型名と一致させるため）
  - コマンド名: `SET`、`HGETALL` など。大文字で、コードとして書く
  - CloudWatch のメトリクス名、設定パラメータ名
- その用語が初めて出てくる箇所では、カタカナの後に英語を括弧で添える
  - 例: エビクション（eviction）

### 用語表（主要なもの）

| 表記 | 英語 | 備考 |

## 7. 「使う可能性がある」機能の厚み（要件 §7 の調整案）
