# フェーズ1: 要件定義（ヒアリング結果）

- 作成日: 2026-11-23
- ステータス: 承認済み（2026-11-23）

## 1. 目的

チーム内で使う Valkey の入門〜実践ドキュメントを作成する。
チームは設計・実装・運用までを担うが、Redis / Valkey の経験者がいない。
本ドキュメントで、メンバーが Valkey を前提とした設計・実装・運用を自力で行えるようにする。

## 2. 書き方のスタンス

- **Valkey / Redis のドキュメントであり、チームのシステム設計書ではない。**
- ただし網羅的なリファレンスは目指さない。
  - チームが使わない機能は省く
  - チームが使う領域は厚く書く
- 例（コード・設定・構成）は、チームと同じ技術スタックで書く（§6）。
- **設計・実装・運用での注意点を重点的に書く。** 本ドキュメントで最も価値を出したい部分。
  - 設計・実装で気をつける点、はまりやすいポイント
  - 障害につながりやすい箇所
  - 見落としやすい箇所（デフォルト設定のまま使うと危ないもの、負荷が上がって初めて表に出る問題など）
  - 書き方: 各章の該当箇所に注意の囲みで書く。さらに、横断的なアンチパターン・障害パターン集の章にまとめる
- 内部構造は、設計・運用の判断に役立つ範囲で解説する。
  - 例: 「なぜ KEYS コマンドは危険なのか」「なぜ小さい Hash はメモリを節約できるのか」の根拠になる程度
  - 実装の詳細までは踏み込まない

## 3. 読者

> フェーズ3で更新: 読者の立場と使われ方を追加した。詳しくは `planning/03-outline.md` の §0。

- Redis / Valkey 未経験のチームメンバー。立場はさまざまで、いずれも業務中の限られた時間で読む
  - 事業会社のエンジニア（ベンダーを管理する立場）: 30 分程度で読む
  - ベンダーの上位者: 1 時間程度で読む
  - 実装者・レビュー担当者: 読み込む
- 前提としてよい知識（本文で説明しない）
  - Python の基礎
  - RDB / SQL の基礎（RDB と比べながら説明してよい）
  - ターミナル操作
  - ネットワーク・サーバーの基礎
  - TLS などセキュリティの一般知識
  - AWS（VPC・セキュリティグループ・IAM など）と AWS CDK の基本
    - ElastiCache に固有の部分だけを説明する
- 読まれ方
  - 最初は頭から通読して学ぶ
  - その後は、必要な章を辞書のように引く
  - そのため、各章は前の章を参照しつつも単独で読めるように書く
- 閲覧環境: GitLab 等の Web UI

## 4. 到達目標

読み終えた読者が以下をできる状態を目指す。

1. Valkey が向く用途・向かない用途を判断できる
2. 要件に応じてデータ型やキーの持ち方を選べる
3. FastAPI アプリに Valkey を組み込み、テストできる
4. 構成（ElastiCache のデプロイ方式、可用性、永続化、コスト）の選択肢とトレードオフを説明できる
5. 運用（監視、トラブル対応、セキュリティ設定、バージョンアップ、メンテナンス）を行える

## 5. チームの想定用途（例と内容の厚みを決める根拠）

- 高速なレスポンスが必要な API 向けのデータストアとして使う
- 正本のデータは RDB にあり、Valkey のデータはバッチで復元できる構成を想定している
  - Valkey を「キャッシュ」ではなく「作り直せる読み取り用データストア」として使う想定
- 次の点はまだ決まっていない（ドキュメントでは判断に必要な知識を解説し、決定はしない）
  - データの更新方式（バッチで全件入れ替え / 差分同期 / API からの書き込み）
  - API からの読み取りパターン（ID で取得 / 一覧・ソート / 検索 など）
  - データ量・アクセス量
  - ElastiCache の構成（Serverless / ノードベース、クラスターモードの有無）

## 6. 技術スタック

| 用途 | 採用技術 |
|---|---|
| 本番環境 | Amazon ElastiCache for Valkey |
| ローカル環境 | Docker Compose |
| アプリ | Python / FastAPI（async） |
| クライアント | redis-py（`redis.asyncio`）。Valkey はプロトコル互換なのでそのまま使える |
| IaC | AWS CDK（言語は Python を想定） |
| 監視 | Amazon CloudWatch |
| 対象バージョン | Valkey 9.1（ElastiCache が対応している最新版。OSS の 9.2 は扱わない）※フェーズ2で決定 |

### データ型・機能の厚み

| 区分 | 対象 | 書き方 |
|---|---|---|
| ほぼ確実に使う | String / Hash / パイプライン / SCAN | 厚く書く |
| あまり使わない | TTL（有効期限） | 一般的なドキュメントより少し薄めにする。コマンドの列挙はしない。仕組みと注意点を中心に書く |
| 使う可能性がある | List / Set / Sorted Set / Stream / トランザクション（MULTI/EXEC）/ Lua スクリプト・Functions / valkey-json / valkey-search（属性検索）| 通常の厚さで書く。どの読み取りパターンなら使うのかを明記する |
| 絶対に使わない | Bitmap・Bitfield / HyperLogLog / Geo / Pub/Sub / キースペース通知 / valkey-bloom / ベクトル検索 | 一覧表で名前と用途を1行紹介するだけにする |

※ 「使う可能性がある」ものの厚みは、フェーズ3で個別に調整する。

## 8. 形式・表記ルール

### 形式

- このリポジトリに、章ごとの Markdown ファイルとして置く
- 図は Mermaid で描く（GitLab で描画される前提）
- ハンズオンはない（概念の説明、コマンド例とその実行結果、コード例が中心）
- ローカル環境（Docker Compose）は概要だけ説明し、具体的な手順は載せない

### 文体・表記

- です・ます調
- 用語はカタカナ表記を優先する（例: エビクション、レプリカ、シャード）
  - 具体的な用語集はフェーズ3で作る
- 公式ドキュメントへのリンクは載せない（ドキュメントの中で完結させる）

### コード例

- 例の題材は、全章で共通の架空の題材に統一する（具体的な題材はフェーズ3で決める。案: EC サイトの商品・在庫・ユーザー）
- 説明したい箇所だけを示す断片を中心にする
- 型ヒントを付ける。本番で気をつける点はコメントで書く
- 設定例は AWS CDK（Python）の L1 コンストラクト（`Cfn*`）で書く
- 料金は料金体系を中心に書き、単価は参考レベルにとどめる

### 各章に必ず入れる要素

- 冒頭: 「要点」（結論を 3〜5 行で。フェーズ3で「この章で分かること」から変更した）
- 本文中: 注意・落とし穴の囲み（通常の引用に太字のラベルを付ける形 `> **注意**`。GitLab 固有のマイナーな構文はなるべく使わない）
  - 何が起きるか / なぜ起きるか / どう防ぐか・どう気づくか、をセットで書く
- 本文中: RDB との対比（「RDB で言うと…」）
- 章末: 「まとめ」
